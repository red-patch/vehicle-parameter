08

问题排序

01

合并策略没有定过 高

Squash 与 merge commit 各用两次，同一仓库的 git log 有两种形状。新人无从判断该跟哪一种。

改法：选一种写进 AGENTS.md。建议 merge commit —— 本项目 PR 数量少、单个 PR 体积大（#5 约 9.5k 行），保留分支边界更有用。
02

发布失败用新 tag 兜底 高

打包配置错误用 v4.5.11 … v4.5.16 六个版本号消化，版本号语义被稀释。

改法：同一版本重打 tag（git tag -f + 重跑 workflow），只有产品行为变化才升 patch。
03

直推 main 的历史 已解决

158 个提交无 PR。10-13 的 ruleset 已挡住新直推（required check、禁强推、禁删，无 bypass）。

状态：不需要动历史。旧提交保持原样是正确选择。
04

分支前缀四套 + 工具前缀两套 中

同一意图两种写法（feat/ 与 feature/），工具生成的分支名不能表达业务。

改法：只留 feat/ fix/ docs/ chore/；AI 会话开分支时手动指定前缀。
05

发布提交写法不统一 低

216 条提交里 179 条符合 conventional commits，37 条不符合，几乎全是 v4.x.y - feat: … 形式。

改法：新脚本已写 chore(release): v$VERSION，保持即可，不追改历史。
06

tag 有轻量有附注 低

14 个轻量、37 个附注。git describe 与 git tag -n 的行为不一致。

改法：发布脚本统一用 git tag -a。
09

按这个顺序改

定合并策略，写进 AGENTS.md

一行规则 + 一次 GitHub 设置即可，收益最大。

发版失败改 tag，不改版本号

在 scripts/release.sh 里加一个 --retag 分支，避免下次又靠升 patch 解决。

分支前缀收敛到四个

在 AGENTS.md 写清 feat/ fix/ docs/ chore/，AI 会话按此开分支。

发布提交与 tag 命令统一

chore(release): vX.Y.Z + 附注 tag，现有脚本已基本到位。
