# 只读远程访问面

资产库此前只对进程内的本机界面开放；本决策**为它开一个跨网络的访问面**：桌面端内置一个只读 HTTP 服务，经隧道（TLS 在隧道边缘终止）供本人手机随时随地访问。**该面严格只读**——手机能查看与对比，不能改名、打标签、删除、填报或触发任何写路径。

关键的连带裁定：`CONTEXT.md` 称资产库目录是「资产的唯一权威来源」，而远程面并不破坏这一点——因为**权威性来自「只有一条写路径」而非「只有一台机器」**。远程面只读，写路径仍唯一地留在本机界面里。因此本决策不是对既有约束的例外，而是它的边界条件：**一旦这个面允许写，「唯一权威来源」即刻失效**，届时必须重新裁定身份键与「永不静默覆盖」（ADR-0002）在跨设备并发下的语义，而不是把本决策就地扩写。

访问控制采用**每设备长期 token**（配对一次、永不过期），名单落资产库目录下的 `_mobile_devices.json` 旁路文件（下划线前缀 = 被资产扫描谓词排除，同 `_asset_tags.json`）。**明确不做**设备吊销 UI：接受「手机即信任边界」；但名单机制保留，因为它是泄露后「换码而不必全员重配」的唯一凭据。服务默认只绑 `127.0.0.1`、只经隧道向外暴露，**局域网内不可见**；启动即监听，但界面必须有显眼的「正在对手机开放」状态与一键关断——即资产库获得了一个**网络暴露开关**，用户须始终知道它的状态。

**已知且已接受的暴露**：TLS 终止在隧道边缘，故**边缘可见请求内容——包括 token 与全部车辆参数**（不只是元数据）。本决策接受这一点：该数据用于投标与配置核对，其敏感度按「商业秘密」而非「个人隐私」对待，且边缘是商业公司而非无保密承诺的公共转发节点。**这条是远程面唯一的实质让渡，任何后续加固的收益都必须相对于它来衡量。**

**Consequences**: 资产库的读面从「进程内」扩到「任意网络」，暴露面因此从「本机安全性」转为「token 保密性 + 隧道边缘可信度」；服务端需要 token 签发/校验与配对流程；`_mobile_devices.json` 进入资产库目录的旁路文件清单。移动端页面由同一服务同源托管，移动端代码独立于桌面构建（不背 antd/xlsx 依赖树），只复用零 Tauri 耦合的领域层。设计细节见 `docs/plans/2026-10-08-mobile-asset-viewer-design.md`。

**Considered Options**: 不设远程面、继续靠导出文件转发——被否：答不了「随时随地查一个值/比两台车」，而这正是需求本身。允许手机端轻编辑——被否：会使「永不静默覆盖」需要在跨设备场景重新发明，成本远超收益。认证交给共享长期码——被否：泄露后唯一补救是换码（全员重配），且无法单设备吊销；共享码反而比每设备 token 更麻烦。认证交给网络层身份（Tailscale 类覆盖网）——被否：中国大陆不存在零账号零 VPS 的可信 HTTPS 路径，而该类方案的控制面可达性不稳定且 iOS 客户端不在中国区 App Store。用 WebRTC 直连替代隧道——被否：同局域网是其退化情形，信令仍需带外 HTTP 端点，且 iOS 对明文源上的 WebRTC 行为无一手文档。

**已评估并否决：应用层端到端加密（Alma `relay.alma.now` 路线）**。评估依据见 `docs/research/2026-10-08-alma-relay-remote-access.md`（该报告解包 `Alma.app` 反编译产物，验证其 E2E 为 P-256 ECDH + AES-GCM、配对码作 PSK、默认开启，中继只见密文路由哈希）。**否决而非"待议"，理由是三条同时成立**：其一，**E2E 与浏览器客户端形态互斥**——E2E 模式下桌面端不再转发 HTTP（Alma 因此把 E2E 限定为原生 App，`connectUrl = null`），而本项目要求「浏览器打开即可用」；其二，**「照搬」这条路不存在**——官方共享中继需账号，且自建中继的服务端代码与文档均未公开，等于自己从帧协议反推实现中继 + 另写原生 iOS App；其三，也是最容易被低估的一条：**在浏览器客户端下，E2E 的保证被"谁发页面、谁控制页面"封顶**——页面经同一隧道下发，恶意边缘可直接替换页面脚本，故「页面明文 + 仅数据密文」只防被动的日志记录，不防主动攻击。该收益相对于上文「已知且已接受的暴露」是边际的，而代价是新增 ECDH 握手、密钥分发与经二维码传递密钥。若将来威胁模型升级（例如数据需对基础设施运营方保密），**正确的动作是改客户端形态或换信任模型，而不是在浏览器客户端上叠 E2E**。
