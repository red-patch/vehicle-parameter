# 自建中继：手机查看的第二条传输

资产库的只读远程面（ADR-0004）此前只有一条出网路径：Cloudflare 具名隧道（`cloudflared`），TLS 在 Cloudflare 边缘终止。本决策**新增第二条、与之并列的传输**：桌面端内置一个出站 WebSocket agent，连到用户自己的服务器上的中继，手机经 `https://<中继>/c/<路由令牌>/` 访问同一个 `127.0.0.1` 只读服务。

中继协议来自开源项目 [yetone/alma-relay](https://github.com/yetone/alma-relay)（MIT，`docs/PROTOCOL.md`）。中继本身可以是官方 Node/Docker 镜像，也可以自己跑；它只做三件事：按 `sha256(路由令牌)` 找到桌面、把 HTTP 帧转发进去、把响应流出来。**端到端加密不适用**——E2E 只在 Alma 自己的原生 App 里实现，浏览器客户端只能走明文；这与 ADR-0004 已接受的暴露同一等级，区别只是边缘从 Cloudflare 换成了用户自己的服务器。

**不变的三条性质照旧**：本机服务仍只绑 `127.0.0.1`（中继是出站连接，不监听端口）、仍然严格只读（只转发 HTTP，不新增写路径）、认证仍是每设备 token。中继多出来的只是「把请求送进来」这一步，权威性来自「只有一条写路径」而非「只有一台机器」的裁定不受影响。

**已知代价（接受）**：

- **协议归属第三方**。桌面端成了 Alma 私有帧协议的一个客户端；协议有文档、有 MIT 许可、官方 e2e 测试里也带参考 agent，但没有任何面向第三方 agent 的兼容承诺。协议改动由我们跟。
- **新增网络依赖**。桌面端原本零网络客户端能力；本决策引入 `tokio-tungstenite`（rustls）+ `hyper` 的 HTTP 客户端栈。这是本项目第一组真实的出站网络依赖。
- **路由令牌在 URL 路径里**。它会进浏览器历史和服务器访问日志；部署时**必须关掉反向代理的 access log 或改写日志格式**，否则等于把桌面密码写进日志。
- **路径前缀**。手机访问的根地址是 `/c/<令牌>/`，移动端页面必须使用相对路径（`fetch('api/...')` 而不是 `fetch('/api/...')`）。P3 尚未开始，此约束在实现时一并遵守。
- **桌面离线时手机看到的是中继的英文 JSON**，不是设计文档里那句中文提示——页面在桌面上，桌面不在就没人能发出那句话。Cloudflare 隧道与 frp 同样如此，不是本方案特有。

**Considered Options**: 只保留 Cloudflare 隧道——被否：用户要求把中转放在自己的服务器上，且不想依赖第三方边缘的账号与条款。用 frp/rathole——技术上更省（零代码、零新依赖），但桌面端要多带一个后端进程与一份配置；本方案把 agent 做成进程内模块，代价是协议耦合与新依赖，换来「不多一个二进制」。照搬 Alma 的端到端加密——被否，理由同 ADR-0004：E2E 与浏览器客户端形态互斥，且页面由同一链路下发时 E2E 的保证被封顶。

**Consequences**: 手机查看有了两条可切换的传输（中继 / 隧道），两者的公网地址互斥，**启用中继时以中继地址为准**，手填的公网地址保留给隧道；中继配置落在资产库目录的 `_mobile_relay.json` 旁路文件（下划线前缀 = 被资产扫描谓词排除）。切换中继地址或更换令牌会让已配对手机需要重新扫码——这是本方案唯一的「撤销」手段，与 ADR-0004「不做设备吊销 UI」的裁定一致。实现见 `src-tauri/src/mobile_relay.rs`。
