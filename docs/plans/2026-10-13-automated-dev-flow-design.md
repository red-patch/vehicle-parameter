# 自动化开发流程 — 设计方案

> 日期：2026-10-13 ｜ 状态：已实施（同日落地；§8 步骤 1–4 完成，§3.3 夜审按需调用）
> 领域术语见 `CONTEXT.md`；执行纪律见 `AGENTS.md`。
> 参考：@wquguru 对 magpie 的拆解（2026-10-12）、@yetone 的工作流自述（2026-10-13）。

## 1. 背景与目标

### 1.1 借鉴来源

yetone 的 magpie（本地 LLM 网关，9-22 起 19 天 9,474 星、2,862 commit、1,204 个版本）宣称代码**由 agent 编写、审查、合并、发布**。剥掉社区/Discord/推特反馈这些外部面，其内核只有四件事：

| 机制 | 做法 |
|---|---|
| CLAUDE.md 极薄 | 只引用两个文件：`AGENTS.md`（路由表）+ `LESSONS.md`（错题本） |
| AGENTS.md = 路由表 | 自己不写规则，只说"干什么活之前翻哪份文档" |
| LESSONS.md = agent 自写的错题本 | 每晚过一遍当天 commit，只找三类：**修完又返工 / 压根不该合 / 验证太糙**。每条 = 一句规则 + 原因 + commit/issue 证据 + `Seen N×` |
| `Seen 3×` 升格 | 同一条教训在 **3 个不同日子**出现 → 从 LESSONS.md 挪进 `code-standards.md`，成为每个 PR 逐条核对的硬规则（magpie 已升格 8 条） |

### 1.2 本项目的实证（写方案前实测）

`git log` 全量 **157 commit，其中 48 条为 fix/修复/revert 类（30.6%）**，且三类返工与 magpie 描述同型：

- **同 bug 分次修**：`b74a971 fix: install bun in Windows build workflow` → `a8986cf fix: install bun for macOS workflow too`（同一问题按平台分两次修）
- **来回返工**：`v4.5.11 productName 回退 ASCII` → `v4.5.14 fix: ASCII productName for WiX compat` → `v4.5.15 fix: Chinese productName + disable WiX`（同一点返工 4 轮）
- **验证太糙**：`24c9ca5` → `441c491` → `889152f` 连续三条"清理编译报错 unused vars"，即提交前未跑 `typecheck`

关键观察：`AGENTS.md` 的「产品名落点（改名时逐条执行）」与「已知坑」两段，**就是手工升格过的 LESSONS**——本项目已在自发做这件事，只是没有机制固化。本方案把它机制化。

### 1.3 目标

1. **让返工可累积**：把"修完又返工/验证太糙"沉淀成带证据的错题本，而非散落在 commit 里；
2. **让教训会升格**：同一教训出现 3 次即变硬规则，防止反复犯；
3. **保住并行安全**：本项目独有痛点是「多个 AI 会话并行改同一工作树」，需要周期性体检抓破坏；
4. **不引入社区/反馈面**：私有库、solo、零 issue/PR，magpie 的 Loop A/B/C 中两条**不适用**，不硬搬。

## 2. 机制设计：LESSONS.md 错题本

### 2.1 文件与分工

新增 `LESSONS.md`（仓库根）。与现有资产分工：

| 文件 | 职责 | 性质 |
|---|---|---|
| `AGENTS.md` | 路由表 + 硬规则 + 已知坑 | **人可读、agent 必读**；稳定、低频改 |
| `LESSONS.md` | 错题本：带证据的教训原始记录 | 高频追加、agent 自维护 |
| `docs/adr/` | 架构决策 | 已存在，不动 |

`AGENTS.md` 顶部「导航指针」新增一行指向 `LESSONS.md`（保持"路由表"定位，不把内容塞进 AGENTS.md）。

### 2.2 单条 LESSONS 的格式

```markdown
### L-<n>: <一句规则>
- 原因：<为什么>。
- 证据：<commit sha / issue>。
- Seen N×（<日期列表，去重到"天">）。
```

### 2.3 升格规则（核心）

- 每次记录时，若同一条规则在**新的、不同的一天**再次命中，`Seen` 计数 +1 并追加日期；
- `Seen` 达到 **3 个不同日期** → 挖规则进 `AGENTS.md` 对应区（行为约束进「执行纪律」，环境坑进「已知坑」，可执行动作进「热点文件/落点」表），并在 LESSONS.md 该条标注 `→ 已升格至 AGENTS.md §<x>（<日期>）`；
- 已升格条目**保留在 LESSONS.md**（作为证据链），但不再重复计数。

### 2.4 三类判定标准（照抄 magpie，消歧到本项目）

一条变化计入错题本，当且仅当满足其一：

- **返工**：同一问题/同一文件的行为，在后续 commit 中被再次改动（如 productName 4 轮）；
- **不该合**：合并/提交了本可被现有检查拦下的东西（如未跑 `typecheck` 就提交 unused var）；
- **验证太糙**：结论缺少证据——测试没回退验证、只整一个平台、没跑项未标注。

### 2.5 「人有约束，agent 有节奏」——防止错题本本身失管

`LESSONS.md` 的**边界**（人定，防失控）：
- 只记录**可验证的工程事实**，不记主观偏好、不记用户文案风格；
- 不覆盖 `AGENTS.md` / `docs/adr/` 已有硬规则，只做发现渠道；
- 条目上限软约束：>60 条触发一次"合并同类项 + 升格/淘汰"整理。

## 3. Loop 设计

三个 loop 里，**工作树体检**与**陈旧物清理**是两个可立即落地的；**夜审**因会话边界受限而改为按需触发（§3.3 说明）。

### 3.1 Loop B — 工作树体检（本项目独有，最高优先级）

**动机**：`AGENTS.md` 已明写"多个 AI 会话会并行改同一工作树"；memory 亦记有"并行会话会切分支，提交/tag/推前必须重确认当前分支"。这是本项目最真实的破坏风险。

**每次检查**（只读，不改）：
1. `git rev-parse --abbrev-ref HEAD`：当前分支是否与预期一致、是否处于 detached/rebase 中间态；
2. `git status --porcelain`：是否有**非本会话**留下的未提交改动/冲突标记；
3. 在**当前工作树**跑 `npm run lint` + `npm run typecheck`，报告是否被并行会话改红；
4. 若发现工作树绿→红，**只报告 + 指认可疑文件**，不自动修（可能是在制品）。

**产出**：仅在有异常时输出一行报告；正常则静默（`noop`）。

**节奏**：动态模式，默认 20–30 分钟一次；或在工作会话切换/提交前手动触发。

**可直接执行的 prompt**（`/loop` 调用或手动喊一次）：

```bash
/loop 工作树体检：查当前分支、git status 是否有非本会话的残留/冲突、并在当前工作树跑 npm run lint 与 npm run typecheck。
只在异常时报告（含指认可疑文件），正常就静默。发现工作树绿转红不要自动修，可能是在制品。
```

### 3.2 Loop C — 陈旧物清理（轻量，只报告）

**动机**：`AGENTS.md`「已知坑」已点名多项陈旧资产，需被周期性提醒而非遗忘。

**检查清单**（`AGENTS.md` 已知坑 + 根目录产物）：
- `README.md` 是否仍是 Vite 模板原文；
- `docs/交互优化设计方案.md` 中已证实陈旧的说法；
- 根目录 `verify_export.csv` 一类临时产物、`~$*.xlsx` 锁文件；
- `.claude/worktrees/` 下陈旧 worktree 快照体积。

**产出**：一份清单式报告（路径 + 一句话现状 + 建议动作），**不自动删改**，由人裁决。

**节奏**：动态模式，低频（如每日 1 次）。

**可直接执行的 prompt**：

```bash
/loop 陈旧物清理扫描：①README 是否仍是 Vite 模板原文 ②docs/交互优化设计方案.md 里 TODO/陈旧说法 ③根目录 verify_*.csv 与 ~$*.xlsx 锁文件 ④.claude/worktrees/ 体积。
输出一份清单（路径 + 现状 + 建议动作），只报告，不删不改。
```

### 3.3 Loop A（夜审）— 暂缓，改按需

magpie 的夜审是自动化的**引擎**，但其运行条件本项目不满足：夜审需要跨天自动跑 `git log` 分析，且 `/loop` 定时任务**仅在 REPL 空闲时触发、7 天过期**；项目又非长期常驻会话。

因此：夜审**改为按需手动触发**——一条可复用的 prompt，在收工或阶段性节点时喊一次：

```
/loop 复盘今天所有 commit：只找①修完又返工的 ②本可被现有检查拦下的 ③验证缺证据的。
逐条按 LESSONS.md 格式追加（含 commit sha 证据 + Seen 计数），Seen 满 3 天则升格进 AGENTS.md。
已有条目重复命中就更新 Seen，不新建。
```

同时，Loop B/C 发现异常时可**顺带**向 `LESSONS.md` 补记一条（如"某文件被并行会话改红两次"），使错题本在无夜审时也能生长。

## 4. 从 magpie 搬到 AGENTS.md 的硬纪律

以下三条 magpie 验收标准，本项目多数尚无，建议直接写入 `AGENTS.md`（成为升格规则的天然候选）：

1. **回退测试（Red check）**：宣称修好前，把旧代码放回去，新写的测试必须**真挂、且挂得明白**（指出哪个行为错了）；编译不过、测试被跳过都不算。
2. **没跑的写出来（Not run）**：没跑的检查**必须显式列为"未跑"**，不能省略——本项目「执行纪律」已有同义句，予以硬化即可。
3. **同 bug 一起修（platform parity）**：`bun` 与 `productName` 两案证明，同类 bug 要**一次性覆盖所有平台/所有实例**，不留尾。

## 5. 与现有资产的关系（不重复造）

- **不新建 code-standards.md**：magpie 该文件对应本项目的 `AGENTS.md`「执行纪律」段，升格目标即此段，避免文件膨胀；
- **不新建 subsystems/**：`docs/adr/` 已承担"改子系统先看决策"的角色，路由表内指向它即可；
- **CONTEXT.md 不动**：术语表与错题本职责正交。

## 6. 验证方式

- `LESSONS.md` 建好后，跑一次**回溯 seed**：用 §1.2 实测的四组历史返工（bun / productName / unused-var / doc-counts）作为首 4 条初始记录，检验格式与升格流程可跑通；
- Loop B 的检查命令逐条手动执行一遍，确认输出可读、无误报；
- 全程**不改业务代码**，故只跑 `npm run lint` 确认无副作用。

## 7. 明确不做（Scope Out）

- ❌ 社区 PR/issue 自动处理、Discord 反馈监听、拉黑低质量贡献者——本项目无对应面；
- ❌ 自动发版/自动合并——发版走 `scripts/release.sh`（人工），CI 已是 tag 触发；
- ❌ 自动删除任何文件/代码——Loop C 只报告；
- ❌ 把 loop 设成高频定时——`/loop` 每 tick 真花 token，且 7 天过期。

## 8. 实施顺序（评审通过后）

1. 建 `LESSONS.md`（含 §6 的 4 条 seed）+ `AGENTS.md` 顶部加一行路由指针；
2. `AGENTS.md`「执行纪律」补 §4 三条硬纪律；
3. 落地 Loop B（工作树体检），手动跑通一轮；
4. 落地 Loop C（陈旧物清理），低频；
5. §3.3 的夜审 prompt 归档到 `AGENTS.md` 或一个 `scripts/` 说明，供按需调用。
